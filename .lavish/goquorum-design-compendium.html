Architecture Map

GoQuorum runs as a single node process that exposes client gRPC and HTTP gateway APIs, while inter-node coordination uses internal HTTP JSON routes. The design is a compact Dynamo model: keys map to a preference list, coordinators fan out reads and writes to N replicas, vector clocks retain concurrent versions, and background repair paths converge replicas after failures.

Runtime process

`cmd/quorum/main.go` loads YAML, opens Pebble, creates membership and the hash ring, wires the HTTP/JSON inter-node client, builds the coordinator, starts gossip if enabled, starts TTL sweeping, starts server listeners, starts coordinator services, then bootstraps failure detection.

Data ownership

The hash ring maps string keys to a preference list of NodeIDs. The coordinator writes to all N preferred replicas concurrently, evaluates W, and can use overflow nodes when sloppy quorum is enabled.

Convergence

Read repair fixes stale replicas after reads, anti-entropy pushes bucketed key ranges when Merkle roots diverge, hinted handoff replays failed writes when targets become active, and TTL sweeper creates tombstones for expired siblings.

OOP Architecture

This view maps the main Go structs and interfaces to their ownership/dependency shape. It is intentionally closer to code than the system map: the process entry point composes long-lived objects, the server adapts external protocols, and the coordinator owns the Dynamo-style data and repair workflows.

Composition root

`cmd/quorum/main.go` constructs concrete dependencies directly. There is no container framework; object lifetime is explicit through start, defer, stop, and shutdown calls.

Adapters

`Server` owns protocol adapters. Client/Admin/Internal APIs translate gRPC, gateway, and HTTP JSON shapes into coordinator, storage, membership, and ring calls.

Core domain object

`Coordinator` is the central domain service. It connects quorum replication to ring placement, storage, RPC, membership, read repair, anti-entropy, and hinted handoff.

Data Plane

The critical path is a coordinator-mediated quorum flow. Every key operation starts with validation and preference-list lookup, then fans out to replicas, merges sibling state, and returns either a causal context or a quorum error.

Write path

1
Validate key/value, copy the supplied vector clock, and tick the coordinator node ID.
2
Create a `storage.Sibling` with value, vector clock, timestamp, tombstone=false, and optional `ExpiresAt`.
3
Ask hash ring for `GetPreferenceList(key, N)` and concurrently write to every preferred replica.
4
Local replica writes call `Storage.Put`; remote replica writes call HTTP JSON `/internal/replicate`.
5
If successes reach W, update Merkle state asynchronously and return the new context. If strict quorum fails and sloppy quorum is enabled, try overflow nodes.
6
Failed remote writes become hints for later replay.

Read path

1
Validate key and compute the preference list.
2
Fan out reads to all N replicas with per-replica timeout and early return after R successful responses.
3
Local reads use `GetRaw` so tombstones are visible to repair. Remote internal reads return the peer's response from `/internal/read`.
4
Merge all siblings by keeping causally maximal vector clocks and deduplicating equal clocks.
5
Trigger read repair when enabled, then filter tombstones from the client result.
6
Return siblings on success, `ErrKeyNotFound` if only tombstones or nothing remain, or a structured quorum error.

Storage Engine

The storage engine wraps Pebble and persists each logical key as an encoded `SiblingSet`. Each sibling carries a value, vector clock, Unix-second timestamp, tombstone flag, and optional expiry timestamp. Storage owns key/value validation, vector-clock reconciliation, sibling pruning, tombstone GC, metrics, and low-level Pebble lifecycle.

Put requestValidate key/value and read existing state through `GetRaw`.
ReconcileUse vector clocks to drop obsolete siblings and retain concurrent ones.
PersistEncode `SiblingSet`, prune metadata, then write to Pebble with sync policy.
Read paths`Get` hides tombstones; `GetRaw` keeps tombstones visible and filters expired live siblings.
Background GCTombstone GC removes old delete markers after retention expires.

Write behavior

  • `Storage.Put` validates key and sibling values, reads existing state with `GetRaw`, reconciles by vector-clock causality, deduplicates by clock string, prunes oversized clocks, and enforces sibling limits.
  • A new sibling supersedes an existing sibling when its vector clock happens after the existing clock. Concurrent siblings are retained.
  • Writes use Pebble `Sync` when `sync_writes` is true and `NoSync` otherwise.
  • Disk-full and I/O errors are classified into storage-domain errors where possible.

Read behavior

  • `Storage.Get` returns client-visible siblings after filtering tombstones.
  • `Storage.GetRaw` is for internal paths that need tombstones and lazy-filters expired live siblings.
  • Storage-level `Scan` walks raw Pebble entries and decodes sibling sets; callers decide how to interpret tombstones and TTL.

Background work

  • Tombstone GC runs when enabled, removes tombstones older than `tombstone_ttl_days`, rewrites keys with remaining siblings, or deletes keys whose only siblings were expired tombstones.
  • Pebble stats are surfaced through storage metrics and admin/debug endpoints.
Verified nuance`Storage.Get` does not filter expired live siblings directly; TTL expiry is handled by `GetRaw` and the separate TTL sweeper.
Vector Clocks

Vector clocks are the causal context for conflict detection. They are represented as node counter maps and used in coordinator writes, sibling reconciliation, read merge, delete tombstones, and CLI context tokens.

Client contextRead returns one or more sibling contexts to the caller.
Coordinator tickWrite/delete copies context and increments the coordinator node counter.
Causality compareHappens-before removes obsolete siblings; concurrent clocks remain.
PruneAge and entry limits bound clock size before persistence.
Conflict resultMultiple maximal clocks are returned as client-visible siblings.
  • Client writes may provide a previous context. The coordinator copies it and ticks its own node ID before creating the new sibling.
  • `HappensBefore`, `HappensAfter`, and equality define whether one sibling dominates another or must coexist as a conflict.
  • Deletes require a non-empty context, tick the coordinator, and write a tombstone sibling so deletion participates in causal conflict resolution.
  • Pruning caps clock growth by age and maximum entries, trading exact long-tail ancestry for bounded metadata.
  • `quorumctl` exposes contexts as base64-encoded JSON so humans can pass a context from `get` or `put` into `delete`.
Design invariantConflict resolution is application-visible. GoQuorum detects concurrent siblings; it does not choose a winning value for the client.
Consistent Hashing

The hash ring spreads keys across configured members with virtual nodes. Each physical node is inserted with 256 virtual nodes in current startup code, and key lookup returns a NodeID preference list used by quorum reads and writes.

Key hashCoordinator hashes the string key onto the ring.
Clockwise walkRing walks virtual nodes until it finds distinct physical NodeIDs.
Preference listFirst N nodes become the strict replica set for quorum work.
Overflow listWhen sloppy quorum is enabled, extra nodes can temporarily accept writes.
RebalanceJoin/leave changes ring membership and relies on anti-entropy to move data.
  • `GetPreferenceList(key string, N int)` returns the first N distinct physical NodeIDs clockwise from the key hash.
  • `GetExtendedPreferenceList(key, N, extra)` supports sloppy quorum by adding overflow candidates beyond the strict preference list.
  • `JoinNode` updates the ring and membership, then triggers anti-entropy to seed the new node.
  • `LeaveNode` drains data to remaining peers using synchronous anti-entropy before removing the node from ring and membership.
  • Debug and admin routes expose ring state and allow ring membership changes.
Corrected signatureThe implementation uses string keys and returns `[]common.NodeID`, not node objects.
Quorum Replication

Quorum replication is the main Dynamo mechanism. N is the replication factor, R is the required read successes, and W is the required write successes. Strong read/write overlap is guaranteed when R + W > N.

  • Writes fan out to all N preferred replicas concurrently and succeed after W successful writes.
  • Reads fan out to all N preferred replicas and return early after R successful responses.
  • Replica timeouts are scoped separately from client request timeout.
  • Successful writes update anti-entropy's Merkle tree asynchronously.
  • Failed remote writes are stored as hints when hinted handoff is attached.
  • Quorum failures return a `common.QuorumError` with required count, achieved count, operation name, and replica errors.

Sloppy quorum

When enabled, strict preference-list failure can be supplemented by overflow nodes from the extended preference list. Hints still target failed strict replicas so writes can be returned home after recovery.

Gossip Membership

Gossip maintains and spreads node membership state over internal HTTP. The state map holds `NodeEntry` records containing node ID, internal HTTP address, status, logical version, and wall-clock update timestamp.

  • Gossip is configured through `gossip.enabled`, `fan_out`, and `interval`. Fanout defaults to 3 and interval to 1 second; enabled defaults false unless configured.
  • On every round, the node randomly selects up to fanout peers from membership and posts its local state to `/internal/gossip/exchange`.
  • The peer merges incoming state, returns its own state, and the caller merges the response.
  • Self entries are never overwritten by remote gossip.
  • When merge accepts a peer update, it also updates `MembershipManager` peer status.
  • Failure detector writes failed status into gossip via `MarkPeer`, which lets failure state propagate beyond the detector's local membership view.
Corrected merge ruleAlthough comments mention version-based LWW, current code uses `UpdatedAt` as the deciding field. `Version` is incremented by `SetSelf` but not used by `Merge` ordering.
Failure Detection

Failure detection sends periodic heartbeats to peers and updates membership status based on success, failure, and configured threshold. It is bootstrapped after the server and coordinator start so peers can call each other.

  • `FailureDetector.Start(peerIDs)` initializes peer health and starts a heartbeat loop.
  • Each heartbeat uses RPC client `Heartbeat`, which maps to internal HTTP `/internal/heartbeat`.
  • Success records heartbeat latency and, if the previous status was failed, detects partition heal and calls `OnNodeRecovery`.
  • Failure records a missed heartbeat and, when status crosses to failed, detects partition and calls `OnNodeFailed`.
  • Current wiring marks failed peers in gossip and triggers anti-entropy when a failed peer recovers.
Operational consequenceFailure detection feeds both membership status and recovery repair. It is not only observability; it changes what repair paths run.
Read Repair

Read repair is request-triggered convergence. After a successful quorum read, the coordinator merges siblings from replicas, then the read repairer compares each replica's response with the merged result and writes missing or stale state back to replicas.

Quorum readCoordinator collects successful replica responses after R is satisfied.
Merge siblingsKeep causally maximal siblings and retain tombstones for repair visibility.
Compare replicasReadRepairer finds replicas that missed the merged sibling set.
Repair writeStale replicas receive `RemotePut` through the same internal replication path.
ModeCan run async in the background or synchronously before returning.
  • Read repair can run asynchronously or synchronously, controlled by config.
  • It uses the same internal remote write path as replication, so repaired siblings go through storage reconciliation on the target node.
  • The coordinator keeps tombstones visible during local raw reads so deletion can repair stale replicas.
  • Repair probability can be tuned; sample config uses probability 1.0.
Design roleRead repair improves hot-key convergence. Anti-entropy still covers cold keys that are not read.
Anti-Entropy

Anti-entropy is the cold-data repair path. It maintains a Merkle tree over local storage and periodically compares Merkle roots with peers. When roots differ, it scans a bucket and pushes matching keys to the peer.

Build treeStartup scans storage and builds the local Merkle tree when enabled.
Schedule bucketScan interval is spread across `2^merkle_depth` buckets.
Compare rootNode asks peer for `/internal/merkle-root` and checks divergence.
Push bucket keysIf roots differ, local keys in the bucket are sent with `RemotePut`.
Triggered syncRecovery and join call `TriggerWithPeer`; leave uses blocking `SyncWithPeers`.
  • Startup builds the initial Merkle tree before scheduling exchanges when anti-entropy is enabled.
  • The scheduler divides `scan_interval` across `2^merkle_depth` buckets and exchanges one range per tick.
  • Current MVP exchanges with all peers rather than selecting only peers responsible for each range.
  • `exchangeWithPeer` compares root hashes through `/internal/merkle-root`; if different, it scans local storage and pushes keys in that bucket through remote put.
  • `TriggerWithPeer` runs all buckets asynchronously for one peer, used for node recovery and join seeding.
  • `SyncWithPeers` runs a blocking drain across all buckets and selected peers, used for graceful leave.
  • `OnKeyUpdate` and `OnKeyDelete` update Merkle state incrementally after successful writes and deletes.
Implementation scopeThe Merkle exchange currently compares global roots before bucket push. It does not yet do recursive subtree diff to minimize transferred keys.
Hinted Handoff

Hinted handoff stores write payloads that failed to reach a target node, then replays them when membership says that target is active again.

  • Hints are in-memory per target node and contain key, sibling set, and creation time.
  • Hints are not stored for self.
  • Per-node hint capacity is 1000; when full, the oldest hint is evicted.
  • Hints older than 24 hours are dropped during replay.
  • The replay loop runs every 30 seconds and attempts delivery only for targets whose membership status is active.
  • Successful remote puts remove hints; failed deliveries remain pending until expiry or later success.
Operational limitHints are process memory only. A node restart loses pending hints, so anti-entropy remains the durable recovery mechanism.
TTL, Tombstones, And GC

TTL and deletion use tombstones so expiry participates in the same causal machinery as explicit deletes. The system separates live-value expiry from tombstone retention.

  • `PutOptions.TTLSeconds` stores `ExpiresAt` on the sibling. Zero means no expiry.
  • `TTLSweeper` scans storage once per minute in current main wiring and rate-limits to 1000 deletes per sweep.
  • When a sibling is expired, the sweeper merges existing sibling clocks, ticks the coordinator node, and calls coordinator `Delete` so a tombstone is replicated with W quorum.
  • Tombstones remain visible internally for conflict resolution and repair.
  • Storage tombstone GC later drops tombstones after configured retention.
Correct mental modelTTL expiry produces a delete operation; tombstone GC is only the later cleanup of old delete markers.
Client API

The client API exposes byte-key/value operations, optional quorum overrides, optional timeouts, and vector-clock contexts. The HTTP gateway maps REST-like routes onto the same protobuf service.

  • Get returns repeated siblings. Multiple siblings mean unresolved conflict and include causal context for client resolution.
  • Put accepts value, optional prior context, optional W override, timeout override, and TTL seconds.
  • Delete requires context so deletion does not blindly erase concurrent writes.
  • Batch get/put provide convenience APIs but still preserve per-key result/error shape.
  • Admin key info returns per-replica state and preference list, useful for debugging repair and conflict behavior.

Error shape

Invalid keys/values, missing delete contexts, quorum failures, and storage errors should surface as distinct failures. Quorum errors include the operation and replica errors so callers can distinguish unavailable replicas from causal conflicts.

Cluster Lifecycle

Cluster lifecycle covers node startup, join, leave, bootstrap, and graceful shutdown. The current startup sequence is important because internal APIs must exist before bootstrap heartbeats can succeed.

ConfigureLoad YAML, apply defaults, validate node, members, quorum, and storage limits.
ConstructOpen storage, build membership, ring, RPC client, coordinator, detector, gossip.
Start loopsStart gossip if enabled, TTL sweeper, server listeners, coordinator services.
BootstrapFailure detector starts after server/coordinator are available for peer calls.
Change clusterJoin seeds via anti-entropy; leave drains data before ring removal.
ShutdownServer stops, coordinator stops, graceful shutdown drains in-flight work.

Actual startup order

  1. Load and validate config.
  2. Open storage and start storage tombstone GC if enabled.
  3. Create membership manager and hash ring from configured static members.
  4. Create HTTP/JSON inter-node client and coordinator.
  5. Create failure detector.
  6. Create gossip and call `gossip.Start()`; it returns immediately if disabled.
  7. Wire failure detector callbacks to anti-entropy and gossip.
  8. Create hinted handoff and attach it to coordinator.
  9. Start TTL sweeper.
  10. Create server, attach gossip, and start gRPC plus HTTP listeners.
  11. Start coordinator services, including hinted handoff and anti-entropy.
  12. Bootstrap cluster and start failure detector.
  13. Wait for SIGTERM or SIGINT and shut down gracefully.

Join and leave

  • Join adds the node to ring and membership, then triggers anti-entropy with the new node for seeding.
  • Leave drains data to remaining peers with synchronous anti-entropy before removing the node.
  • Notify-leaving route updates membership status to leaving on peers.
Configuration

Configuration is loaded from YAML, defaults are applied, then invariants are validated. It covers node identity, cluster members, quorum, storage, repair, anti-entropy, connection, server, TLS, rate limiting, and gossip.

  • `node.node_id` is required, must be 1-64 chars, and can contain alphanumeric, underscore, and hyphen.
  • `cluster.members` must be non-empty and include self.
  • `quorum.N` cannot exceed configured cluster size.
  • Code default quorum is N=3/R=2/W=2, but sample `config.yaml` sets N=1/R=1/W=1 for single-node development.
  • Cluster heartbeat defaults: interval 1s, timeout 2s, failure threshold 5, bootstrap timeout 60s.
  • Server defaults: gRPC `:7070`, HTTP `:8080`.
  • Gossip defaults: fanout 3, interval 1s, enabled remains false unless set.
Config footgunIf quorum config is omitted in a single-node cluster, the default N=3 will fail validation because N exceeds cluster size.
TLS Security

TLS configuration is shared across server and connection layers. The server can load TLS credentials for gRPC, and the HTTP client can load a client TLS config for internal calls when connection TLS is enabled.

  • Server TLS is applied as gRPC credentials when `server.tls.enabled` is true.
  • Connection TLS changes internal HTTP scheme to `https` and loads client TLS config.
  • If client TLS config loading fails, the internal client logs a warning and proceeds without TLS; callers will then see connection or certificate failures if peers require TLS.
  • The design goal is mTLS-capable public and inter-node traffic, but route-by-route authorization is not the dominant mechanism in current code.
Backup And Restore

Backup and restore wrap Pebble checkpointing and archive extraction. The operational surface currently appears as bare HTTP handlers backed by `AdminAPI.BackupDB` and `AdminAPI.RestoreDB`.

  • `POST /admin/backup` accepts `dest_dir` and returns the archive path.
  • `POST /admin/restore` accepts `archive_file` and `dest_data_dir` and returns status ok on success.
  • The design notes describe future or intended admin gRPC/CLI integration, but the current protobuf admin service does not include backup/restore RPCs.
  • Restore must be treated carefully operationally because replacing a live Pebble data directory requires lifecycle coordination outside the storage engine.
Corrected surfaceDo not document backup/restore as current `quorumctl` commands. They are server HTTP admin routes today.
Observability

Observability spans Prometheus metrics, admin health, cluster info, debug routes, and structured domain counters across storage, coordinator, failure detector, and repair.

  • `/metrics` serves Prometheus exposition through `promhttp.Handler()`.
  • Admin `GetMetrics` also returns Prometheus-format metrics through the gRPC/gateway admin API.
  • Health checks include node ID, uptime, version, and component checks.
  • Coordinator metrics track read/write latency, request totals, success counts, quorum failures, and observed sibling counts.
  • Storage metrics track read/write latency, bytes read/written, corrupted reads, write errors, tombstone GC, vector-clock pruning, and sibling pruning.
  • Failure detector metrics track heartbeat successes/failures and partition suspected/healed events.
  • Anti-entropy metrics track exchanges, failures, scan duration, and keys exchanged.
CLI Tool

`quorumctl` is a gRPC terminal client for data operations and operational inspection. It connects to a node with `--addr`, creates both client and admin gRPC clients, and prints human-readable results.

CommandCurrent purpose
`get <key>`Fetch siblings and show context tokens.
`put <key> <value>`Write a value and print the new context.
`delete <key> <context>`Write a tombstone using a base64 JSON context.
`status`Show node health and cluster status.
`ring`Show ring or cluster placement information.
`key-info <key>`Show replica detail and preference list for a key.
`compact`Trigger Pebble compaction through admin API.
