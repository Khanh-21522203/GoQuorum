Dynamo-style key-value store in Go

A compact atlas for understanding the GoQuorum project.

GoQuorum is a masterless distributed key-value store with consistent hashing, tunable quorum replication, vector clocks, read repair, hinted handoff, anti-entropy, Pebble-backed persistence, and production-facing observability.

Overview

The project is organized around one long-running node process. Each node exposes public APIs, participates in peer-to-peer replication, tracks cluster state, and repairs divergence in the background.

The mental model

A client request enters through gRPC or the HTTP gateway. The server layer validates input and delegates to the coordinator. The coordinator maps keys through the hash ring, fans out to replicas, evaluates read/write quorum, then relies on repair loops to keep replicas convergent after failures or partitions.

Stored values are not simple last-write-wins rows. Each key maps to a sibling set, and each sibling carries a vector clock. This is the core mechanism that lets the system detect causality, preserve concurrent writes, and let clients resolve conflicts.

Dynamo Model

The design follows the classic Dynamo tradeoff: availability and partition tolerance first, with explicit mechanisms for detecting and repairing divergent versions.

placement

Consistent hashing

Keys are routed through a virtual-node ring. Each operation gets a deterministic preference list of replica nodes.

quorum

N/R/W semantics

Replication factor N, read quorum R, and write quorum W control the availability and consistency tradeoff.

causality

Vector-clock siblings

Dominated versions are removed. Concurrent versions remain as siblings until a client writes back a resolved value.

repair

Read repair

Reads compare replica responses and push merged state back to stale replicas after the client-visible read path.

availability

Hinted handoff

Unavailable targets get in-memory hints. When they recover, the node replays buffered writes to close the gap.

convergence

Anti-entropy

Merkle roots detect cold divergence, then bucket scans push missing or stale keys between peers.

How the pieces fit together

  • Ring The hash ring turns a key into an ordered preference list. In a three-node cluster with N=3, a write normally targets all three owners for that key.
  • Write The coordinator ticks the local vector clock, writes locally if this node is an owner, sends replica writes to peers, and returns after W successful acknowledgements.
  • Read Reads query the same owners in parallel and return after R successful responses. Responses are merged by vector-clock dominance before going back to the client.
  • Siblings If two writes are concurrent, neither clock dominates the other. Both values stay in the sibling set so the client can resolve the conflict explicitly.
  • Repair Read repair fixes replicas touched by reads. Hinted handoff covers temporary write failures. Anti-entropy catches cold keys and post-partition divergence.

Lifecycle

The node lifecycle is explicit in cmd/quorum/main.go.

1. Load config and open storage

YAML config defines node identity, cluster members, server addresses, quorum settings, repair intervals, storage limits, and TLS settings. Storage opens a Pebble database under the node data directory.

2. Build cluster primitives

Membership state, hash ring, RPC client, coordinator, failure detector, gossip, hinted handoff, and TTL sweeper are constructed and wired together.

3. Start serving

The server starts gRPC and HTTP listeners. The coordinator starts anti-entropy and hinted handoff. Bootstrap waits for cluster quorum before the node becomes ready.

4. Drain on shutdown

Graceful shutdown stops the API surface, waits for in-flight work, and syncs data to remaining peers before leaving the cluster.

Implementation Map

Open these files when you want to understand or change a behavior.

Quorum read/write behavior internal/cluster/coordinator.go

Start here for Put, Get, Delete, BatchGet, BatchPut, preference-list routing, replica fanout, quorum evaluation, sloppy quorum, and repair trigger behavior.

Storage encoding and sibling reconciliation internal/storage/engine.go

This layer loads raw sibling sets, reconciles vector-clock dominance, prunes excessive siblings, encodes values, validates CRC32, and applies TTL/tombstone filtering.

Peer communication internal/cluster/rpc_client.go

The concrete client name is historical. Inter-node calls use HTTP/JSON for replicate, read, heartbeat, Merkle root, and leaving notification.

HTTP and gRPC server wiring internal/server/server.go

Registers public gRPC services, grpc-gateway routes, internal HTTP routes, health, metrics, debug, backup, restore, TLS, and rate limiting.

Background convergence anti_entropy.go, read_repair.go, hinted_handoff.go

These files contain the system's eventual-consistency machinery. They are best read together because each closes a different failure window.

Boundaries

A few practical constraints matter when evaluating this project.

Hinted handoff is in-memory only. If a node restarts before hints replay, anti-entropy is the recovery mechanism.
The system stores concurrent siblings intentionally. Application clients must resolve conflicts by reading all siblings and writing back a context that dominates them.
Inter-node transport is HTTP/JSON even though the concrete client type is named GRPCClient. The public API still exposes gRPC.
